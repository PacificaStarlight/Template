# Masterplan · 总体规划

> Ponytail 让代码变少；Masterplan 让剩下的代码待在对的位置。
> **最少的东西，放在对的位置。**

本技能一旦用于某次设计或改动，整个任务期间保持：新增文件、改接口、加依赖之前，
先过一遍落位协议；任务结束或用户说"停"即退出。

## 0. 先读地图，再动代码

一行改动、纯局部 bug、重命名：不用走全套；直接用 ponytail 的阶梯（若未安装，就用"最小改动"原则）。
任何非平凡改动之前：

1. **找地图**：`ARCHITECTURE.md`、`框架设计.md`、`docs/` 里的架构文档，或项目自己的约定。
   有就读；没有且项目只有一两个文件，跳过——代码本身就是地图。
2. **追真实流程**：架构不是目录树，是实际的 import / 调用图。读入口、读你要改的模块、
   grep 这个函数的每一个调用者。**先读懂，再落位**；小 diff 放错地方是第二个 bug。
3. **一句话说清变化**：`当 ___ 变化时，___ 必须跟着变。`
   填不出来，说明还没理解这次改动，先别写。
4. **判断谁在操作**：是用户手动改、ponytail 在约束数量、还是其他 skill 在操作？
   只看可观察的事实（环境里有没有这个 skill、请求有没有点名、仓库实际改了什么）；
   不确定就按"用户手动操作"处理。

## 1. 唯一的核心问题

> **什么会变？它从哪个缝进来？**

设计不是"套模式"，而是：

1. 找出变化点
2. 把稳定部分和变化部分分开
3. 在边界上定义一个缝（seam）
4. 让调用方只依赖缝
5. 让"加一个新变体"不需要改稳定代码

一个抽象如果回答不了"它隔离了什么变化"，它就是装饰。删掉。

### 怎么找变化点（map / review 时）

- **看入口**：用户/系统能触发哪些操作？从入口追到效果，不读无关文件。
- **看分支**：`if/else`、`switch`、`instanceof`、类型判断密集处 = 隐式变化轴。
- **看重复**：同一条规则出现在两处 = 缺一个单一真相。
- **看一起改**：每次需求都同时改的几个文件 = 缺一个归属模块或缝。
- **看依赖**：向上 import、环、全局查找 = 依赖方向错了。

## 2. 三条定律

### 定律一：变化有址

- 同一种知识/规则只存在一处（DRY 是"知识唯一"，不是"行数唯一"）。
- 同一种变化只有一个入口（SRP：一个改动的理由；OCP：加变体不改稳定代码）。
- 判据：改这条规则只改一个文件；加一个变体只加一个文件 + 一行登记。
- 反例：折扣规则在订单服务和促销服务各写一遍；加一种支付方式要改 if/else 链。

### 定律二：依赖向稳

- 高层策略不 import 低层细节；稳定代码不 import 易变代码。
- 需要反向时，用注入、事件、回调，把线接在装配层。
- 判据：画 import 图，箭头只能从易变指向稳定；出现环或向上箭头 = 结构错误。
- 分层项目里的特例：**依赖只能向下**（L3 业务 → L2 复用 → L1 内核 → L0 插件）。

### 定律三：最小充分

- 没有第二个真实变体，不建缝；没有当前需求，不建扩展点。
- 每加一层间接，必须能指出它今天挡住了哪种变化；指不出就删。
- 判据：删掉这个接口/工厂/基类，当前需求还能满足吗？能 → 删。
- 这不是反对设计，是反对为想象中的未来设计（KISS + YAGNI）。
- "真实"包括：今天已有两个实现、需求明确点名了第二个、或硬外部边界要求可替换。
  不包括"以后可能会有"。

> KISS 是总目标；SOLID/DRY 是手段。手段服务于"下次改动更便宜"，不是考核指标。
> 补充两条：**组合优于继承**（能"有一个"就别"是一个"）；**最少知识**（只和直接朋友说话，
> 别隔着三层取值）。

## 3. 落位协议

每个非平凡改动都走这六步。

### Step 1 — 分类

| 类型 | 判据 | 做法 |
|---|---|---|
| **A. 现有轴上的新变体** | 系统已有同类东西，且已有 ≥2 个实现或你正在加第二个 | 找到现有缝，只加变体 + 登记 |
| **B. 新变化轴** | 系统以前没有这个维度（如给单机游戏加联机、给无多语言项目加本地化） | 确认是"今天真需要"；是 → 在边界建**一个**缝，不全库改造；否 → 先内联 |
| **C. 一次性改动** | 想不出第二个真实用例 | 内联在归属模块，不建抽象 |
| **D. 缺陷修复** | 报告的是症状 | 修共享根因，grep 所有调用者；不要在报错路径上打补丁 |

**缝的演进阶梯**（不要一步跳到工厂）：

```
1 个变体：内联分支
  → 同一职责里可读性差：提取方法
  → 第 2 个真实变体：提取接口/基类
  → 创建逻辑开始变化，或调用方不该知道具体类：移走创建（工厂/注册表）
  → 变体由配置/部署决定：注册表移到配置
```

**小例**：结算流程里 `if (type === 'wechat') ... else if (type === 'alipay') ...`
→ 第二个支付方式出现时，抽 `PaymentMethod.pay(order)`；
→ `Checkout` 只依赖 `PaymentMethod`；
→ 新增 `UnionPay` = 新文件 + `registry` 一行；
→ 加法测试：`Checkout` 未改。

### Step 2 — 找归属

- 归属模块 = **唯一改动理由**与这次变化匹配的模块。
- 两个模块都声称归属 → 边界错了。先修边界，再放功能；不要为了两边都满意而复制功能。
- 没有模块归属 → 要么这是新模块（说明理由），要么你还没读懂现有模块。
- 命名：模块名说**职责**，不说技术栈。`Audio` 可以；业务模块里的 `Manager`/`Utils`/`Common`
  这类空名通常说明职责没想清（基础设施服务除外）。

### Step 3 — 找缝

- **有现成的缝？** 用现成的。只读接口 + 一个样板变体，不读全项目。
- **没有，但这是第二个真实变体？** 现在建缝：放在稳定策略与易变细节的边界上，
  接口用**调用方的语言**表达（调用方不该知道"MySQL"才能保存订单）。
- **只有一个变体，也没有硬约束？** 内联。可以留一行 `// seam: 出现第二个 X 时再抽`，
  但不要提前写接口。
- **缝要窄**（ISP）：只放调用方真正需要的方法。胖接口会逼出空实现和 `throw not supported`。
- **一条轴一个缝**：两个维度独立变化就两个缝（桥接），不要合成一个上帝接口。

### Step 4 — 写变体

- 新文件放在槽位指定目录，照抄样板。
- 只实现缝的契约，不加"以防万一"的公开方法。
- **遵守 LSP**：同样的前置/后置条件、不抛调用方没预期的异常、不破坏不变量。
  如果某个变体做不到，说明缝错了——修抽象，不要在调用方加 `if (type === ...)`。
- 变体特有的知识留在变体内部。调用方一旦需要 `instanceof` / 类型判断，接口就不完整。
- 需要外部依赖 → 注入；不向上 import，不摸全局。

### Step 5 — 登记

- 每个扩展恰好一个登记点，而且**看得见**（装配根、注册表、配置表）。
- 登记是一行/一条。加一个变体要改 3 处以上，说明缝不完整。
- 登记 ≠ 接线：登记说"这个变体存在"，接线说"这里用它"。接线只发生在装配层。
- 不要用隐式自动发现，除非项目已经在用且有类型检查。显式胜过聪明。

### Step 6 — 验证

| 测试 | 问题 | 失败说明 |
|---|---|---|
| **加法测试** | 加这个变体改了稳定代码吗？（只允许一行登记） | 缝的位置错了 |
| **删除测试** | 删掉变体文件 + 登记行，还有别处报错/悬空吗？ | 有隐藏依赖 |
| **陌生人测试** | 新人只看地图 + 接口 + 一个样板，能在 2 分钟内加出同类变体吗？ | 地图/命名/样板有问题 |
| **最简测试** | 删掉新加的某层间接，需求还能满足吗？ | 那层是装饰 |

测试失败，修结构，不要改测试。如果失败不是小修能解决的，进入 §8 结构重评；
不要用更多补丁把失败盖住。

## 4. 项目地图：把"预设位置"写下来

地图不是架构散文，是**索引**。它回答一个问题：**我要加 X，去哪？**

### 什么时候建

- 多模块/多层、多人协作、或源码超过 ~10 个文件。
- 已有架构文档（如 `框架设计.md`）→ **更新它，不要新建第二份真相**。
- 小项目跳过；代码就是地图（YAGNI）。

### 最小内容（一页）

1. **分区**：每区的职责、允许 import 谁、禁止谁 import 它。
2. **槽位表**：

   | 要加的东西 | 放哪里 | 实现什么 | 在哪登记 | 样板文件 | 不要碰 |
   |---|---|---|---|---|---|
   | 支付方式 | `payments/` | `PaymentMethod` | `registry.ts` 一行 | `WechatPay.ts` | 结算流程 |

3. **不变量**：3~7 条必须始终成立的规则，每条带检查方式（grep/脚本/测试）。
4. **改动路线**：最常见的 3~5 种改动，写成步骤。

### 两条硬规则

- **没有样板文件的槽位不算槽位。** 槽位 = 一个能跑的样板 + 一个登记点（第一个变体写完后，它就是样板）。
- **没有检查方式的不变量不算不变量。** 写不出怎么验，就删掉这条。

### 地图纪律

- 只写代码**现在**的样子，不写愿望。每一条都要对得上代码。
- 结构变了就在同一次改动里更新地图。过期地图比没有地图更糟。
- 每节控制在一屏内；细节放样板文件里。

## 5. 缝的形态（查表，不是菜单）

**先有缝，后有模式名。** 模式是缝的词汇，不是目标。

| 变化/需求形态 | 缝的形态 | 调用方看到 | 不要用于 |
|---|---|---|---|
| 同一行为多种算法，运行时可换 | 策略 Strategy | 一个接口 + 一组实现 | 只有一个算法时 |
| 创建逻辑复杂/要选择实现 | 工厂 Factory | 创建函数/接口 | 每个类配一个工厂 |
| 功能逐层叠加、顺序可组合 | 装饰器 Decorator | 同接口的包装对象 | 简单 for 循环能解决时 |
| 访问控制/前后增强 | 代理 Proxy | 同接口 | 与装饰器混用 |
| 多个节点依次处理 | 责任链 Chain | 一个处理入口 | 节点固定且只有一个时 |
| 接口不匹配 | 适配器 Adapter | 目标接口 | 拿它做功能增强 |
| 复杂子系统要简化入口 | 外观 Facade | 一个高层方法 | 包成上帝类 |
| 一对多通知 | 观察者/事件 Observer | 订阅/发布 | 需要返回值或强顺序时 |
| 请求要排队/撤销/记录 | 命令 Command | 命令对象 | 只是直接调用时 |
| 行为由状态决定 | 状态 State | 状态对象 | 枚举 switch 更清楚时 |
| 多个维度独立变化 | 桥接 Bridge | 两个抽象的组合 | 只有一个维度时 |
| 固定骨架、步骤可变 | 模板方法 Template | 基类 + 钩子 | 骨架本身还在变时 |
| 全局唯一、进程级、无副作用 | 单例 Singleton | 全局访问点 | 有业务状态/场景级生命周期时 |

表里没有的模式不代表不能用；先能说出变化轴，再决定名字。
判断不了用哪个：回到 §1。**说不清隔离了什么变化，就别用。**

## 6. 反模式：原则表演

- **原则表演**：为了"符合 SRP"把类拆成七个，但改动理由只有一个。判断：能说出一个只改其中一个的真实变化吗？说不出，它们就是一个职责。
- **想象出来的扩展点**：一个实现配一个接口、一个产品配一个工厂、一个永不变化的值配一份配置。判断：今天有第二个具体变体吗？没有就内联。唯一例外是硬外部边界（SDK、平台、持久化、网络），但要点名约束。
- **过度 DRY**：把长得像的代码合并。判断：是同一份知识**且**同一个改动理由吗？任一为否，就别合。布尔开关参数是坏合并的味道。
- **分层表演**：只转发调用的层、什么也不加的基类、只管一个东西的 Manager。判断：删掉它，有东西变难吗？没有就是装饰。
- **抽象泄漏**：调用方要了解实现细节、捕获实现异常、传实现特定的 flag。修接口，不要写文档解释泄漏。
- **隐式接线**：全局查找、自动注册、字符串 key、裸事件名。把线放到一个看得见的装配点，并给名字加类型。
- **模式崇拜**：因为书上有这个模式而用。模式是结果，不是目标。
- **KISS 误读**：KISS 不是不设计，是不要没有当前价值的复杂度。一个好的缝可能比一堆 if 更简单。

## 7. 与 ponytail 的分工

> 本技能不依赖 ponytail 安装；下面只是分工说明。

- **ponytail 管数量**：要不要存在？能少到什么程度？
- **masterplan 管位置**：既然要存在，放哪？依赖朝哪指？
- 两者都反对想象出来的抽象。masterplan 多加一个条件：**抽象必须有当前变体，且能命名它隔离的变化。**
- 冲突解决：ponytail 说"一个实现不要接口"；masterplan 只在**硬外部边界**允许一个实现（SDK/平台/持久化/网络），内部想象出来的缝不允许。
- 推荐顺序：**先问要不要（ponytail）→ 再问放哪里（masterplan）→ 再问能少到什么程度（ponytail）→ 最后验落位（masterplan）。**
- 一句话：**最少的东西，放在对的位置。**

### 兼容与容错：先判断谁在操作

本技能不假设 ponytail 存在，也不假设它是最初描述的那个版本。先看当前环境，再决定用哪套规则：

| 情况 | 怎么处理 |
|---|---|
| 没装 ponytail | 一律按用户手动操作处理；不引用、不模拟它的规则。数量判断交给用户/宿主默认规则，落位仍按本技能执行。 |
| ponytail 版本/行为不同 | 以已安装版本的当前行为为准；§7 只是分工说明，不复制它的具体规则。若它的改动让 §7 的分工不再成立，按当前行为重新划分，不要硬套旧口径。冲突时：位置听 masterplan，数量听当前 ponytail。 |
| 其他 skill 在操作 | 先识别它的目标和边界；不要把它当成 ponytail。冲突时：用户明确指令 > 该 skill 的显式规则 > 本技能默认。 |
| 用户手动改 | 默认就是人为操作。不要猜测"这是 ponytail 想让我做的"；按用户说的做，用地图和四测试检查落位。 |
| ponytail 已安装但未启用 | 安装 ≠ 启用。不要假设它已生效；按用户当前指令和本技能落位。 |
| 不确定谁在操作 | 按"用户手动操作"处理，并在输出里用一行说明你的假设。 |

判断顺序：**先看有没有其他 skill 在操作 → 再看 ponytail 是否安装/启用 → 都没有就按用户手动操作。**

不确定时，先跑 `map`（只读）重建地图；不要边猜边改代码。

原则：**安装 ≠ 启用**。**只依据能观察到的事实判断**（环境里有没有这个 skill、请求里有没有点名、仓库里实际改了什么），不依据对别的 skill 的想象。

## 8. 结构重评：放不进去，就改结构

落位协议假设"现有结构还成立"。如果新需求证明这个假设不成立，**不要硬塞**；先重评，再动手。

### 什么时候触发

- 新功能找不到任何现有槽位，或要同时改 3 个以上稳定模块。
- 需要合并两个模块/功能，或把一个模块拆成两个。
- 新变化轴横跨多个现有分区（横切关注点）。
- 现有不变量与新需求直接冲突。
- 删除测试失败：删掉一个功能后，别处还有悬空引用。
- 同一条知识已经在 3 处以上重复。
- 用户明确要求大改/融合/重写；或其他 skill/人的改动已经让地图过期。

### 重评步骤

1. **停下来说清楚**：一句话写出"当前结构为什么装不下这个需求"。不要先写代码。
2. **重建现状图**：按 §1 的"怎么找变化点"扫一遍，列出分区、缝、依赖方向、变化轴。以代码为准，不以旧地图为准。
3. **找最小结构改动**：只改被新需求逼出来的那一处：
   - 移动边界（拆分/合并分区）
   - 新增一条轴/一个缝
   - 替换错误的抽象
   - 把横切关注点提升为显式缝
4. **给迁移路径**：哪些移动、哪些保留、哪些删除；分几步；每步后旧功能仍可用。
5. **给选项**：如果改动大，至少给两个方案——
   - 最小补丁：不改结构，接受一点重复/例外，标明天花板；
   - 结构重评：改结构，给出迁移成本和风险。
   选择权交给用户；不要静默重写整个项目。
6. **更新地图**：新分区、新槽位表、新不变量、旧结构的废弃说明，同一次改动里完成。
7. **验收**：四测试 + 旧功能回归 + 新不变量检查。重评不是重建，旧结构里仍然成立的部分要保留。

### 重评的边界

- 重评只改"新需求逼出来的结构"，不是借机把项目重写成理想架构。
- 说不出"不改就会怎样"的结构改动，不做（定律三仍然成立）。
- 大改之前先给用户看目标结构和迁移步骤；用户确认后再动代码。
- 如果用户只是要一个快速补丁，给补丁，但把"结构债"和触发条件写清楚。

## 9. 给人用的路径（选做，但推荐）

目标：一个人不读全项目，也能快速加/改/删功能。

1. **一个功能一个家**：一个文件夹/文件 + 一行登记。删除 = 删文件 + 删登记行。
2. **一个槽位一个样板**：新变体照抄样板；读接口 + 样板，不读全世界。
3. **可预测的命名**：模块名=职责；文件名=东西；事件名=`域/动作`；业务模块避免 `Manager`/`Utils`/`Helper` 这类空名（基础设施服务除外）。
4. **接线可见**：唯一的装配根/注册表；没有隐藏全局。人一眼能看完全部连线。
5. **不变量有检查**：依赖方向、禁止向上 import、单一真相——用 grep/脚本/测试守住，不靠记忆。
6. **一页地图**：分区图 + 槽位表 + 改动路线。人两分钟内找不到答案，是地图的错，不是人的错。
7. **稳定内核要小**：所有人都依赖的部分保持小（几百行），读它才便宜；便利方法踢出内核。
8. **改动配方**：最常见的 3~5 种改动写成步骤："加一个变体：建 X → 实现 Y → 登记 Z → 完"（按项目替换成"加一个面板/支付方式/事件"）。

度量：**两分钟测试**——新人只看地图和命名，能在两分钟内回答"这个功能放哪？"
做不到，修地图/命名，不要怪人。

## 10. 输出

非平凡改动，用几行报告：

```
变化轴：___（现有轴 / 新轴 / 一次性）
落位：zone / seam / registration
结构增量：新文件、新缝、地图更新
验证：加法 / 删除 / 陌生人 / 最简
没做：刻意没抽的东西 + 什么时候再抽
```

代码优先，结构说明其次。用户要完整评审时再展开；否则不要写架构散文。

## 11. 模式

- `map`：从代码建/刷新项目地图（分区、槽位表、不变量、配方），逐条对代码验证。
- `place`：落位一个改动（用户说"加/改/删一个功能"时的默认）。
- `review`：按 §2/§6 审一个 diff 或模块，报违规 + 最小修法（带 file:line）。
- 未指定：从请求推断；拿不准用 `place`。

## 12. 收尾检查

- [ ] 能用一句话说出变化轴。
- [ ] 改动落在拥有这个改动理由的模块。
- [ ] 加变体没有改稳定逻辑（最多一行登记）。
- [ ] 删变体只需要删自己的文件 + 登记行。
- [ ] 同一条知识只存在一处。
- [ ] 依赖仍指向稳定；没有新的向上 import 或环。
- [ ] 每个新抽象都有当前第二个用例，或点名的硬约束。
- [ ] 地图/槽位表仍然为真（结构变了就更新）。
- [ ] 陌生人能在两分钟内从地图找到槽位。
- [ ] 没有用说不清变化轴的模式。
- [ ] 如果改动放不进去，我触发的是结构重评，而不是硬塞。
- [ ] 我没有假设 ponytail 存在或版本一致；操作主体判断有依据。
